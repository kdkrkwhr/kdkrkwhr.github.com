### TL;DR

* 기존 Python 게임 규칙을 유지하면서, 사용자가 조작할 화면과 Anna 연결 부분을 추가했다.
* 게임 규칙은 다음 상태를 계산하고, Anna 연결 계층은 사용자별 저장과 도구 실행을 맡는다.
* 화면이 보이는 것, 행동이 실행되는 것, 다시 열었을 때 기록이 남는 것은 각각 확인해야 했다.

### 화면과 게임 규칙 사이에 연결 계층을 두었다

[Anna 공식 개발자 안내](https://anna.partners/developers)는 HTML·JavaScript·CSS로 만든 앱 화면과 실행 도구를 함께 제공하는 방식을 소개한다. 노트버디에서는 화면에 JavaScript를 사용하고, 기존 게임 규칙은 Python으로 유지했다.

현재 코드의 역할은 크게 네 부분이다.

| 부분 | 맡는 일 |
| --- | --- |
| 앱 화면 · `anna/bundle/` | 친구와 상태 표시, 버튼·대화·그림 입력, AI 요청 |
| Anna 연결 · `notebuddy_plugin.py` | 게임 도구 요청 수신, 사용자별 저장 읽기와 조건부 저장 |
| Python 실행 · `game_worker.py` | 요청을 공통 규칙에 전달하고 화면에 필요한 결과 구성 |
| 공통 게임 규칙 · `engine/game_api.py` | 돌봄·성장·보상 조건을 검사하고 다음 상태 계산 |

Anna의 실행 도구 체계를 **Executa**라고 부른다. 노트버디에서는 앱 화면이 Host API를 통해 이 Python 도구를 호출한다. 게임 행동이 규칙과 저장소에 연결되는 흐름은 다음과 같다.

    UI["Anna 앱 화면"] -->|게임 행동| Tool["Executa · Python 도구"]

이렇게 나누면 돌봄 규칙을 고칠 때 화면이나 Anna 저장 API까지 함께 고칠 필요가 줄어든다. 반대로 저장 방식이 달라져도 포만감이나 성장 조건을 플랫폼마다 다시 작성하지 않아도 된다.

### ‘밥 주기’ 버튼 한 번이 저장되기까지

이미 친구가 있는 사용자가 먹이 버튼을 눌렀다고 해 보자. 대략 다음 순서로 처리한다.

1. 화면이 행동의 **요청 ID**를 만들고 게임 도구를 호출한다.
2. 도구가 해당 사용자의 저장 데이터와 저장 버전을 읽는다.
3. Python 규칙이 행동 가능 여부를 확인하고 다음 상태를 계산한다.
4. 읽어 온 저장 버전이 여전히 유효한지 확인하면서 결과를 저장한다.
5. 저장에 성공한 결과를 화면에 표시하고, 설정에 따라 AI 반응을 요청한다.

규칙을 호출하는 핵심 형태는 아래처럼 단순하다. 주변의 인증·저장 처리는 생략한 예시다.

```python
candidate = transition(
    state,
    "feed",
    context,
    actor_id="1",
    request_id=request_id,
)
# candidate.state는 계산 결과다.
# 실제 저장 여부와 저장 충돌 처리는 Anna 연결 계층이 담당한다.
```

`context`에는 규칙 데이터, 현재 시각, 난수와 ID 생성 방법을 전달한다. [공통 API](https://github.com/kdkrkwhr/notebook-pets/blob/cba0513803a96350d8807c2dc156b27ed3c8efbb/engine/game_api.py)는 파일을 열거나 Anna에 접속하지 않고 입력된 상태로 다음 상태를 계산한다. 현재 Anna 도구도 이 API에 상태를 직접 전달한다.

저장 충돌에는 두 가지 장치를 사용한다. 기존 저장을 덮어쓸 때는 읽었던 버전인 **ETag**를 함께 보내고, 그사이 다른 행동으로 데이터가 바뀌었다면 다시 읽고 계산한다. 같은 행동의 재시도에는 같은 요청 ID를 사용하고, 처리 기록을 게임 상태와 함께 남겨 중복 적용을 막는다.

이 장치가 모든 동시 실행 문제를 해결한다는 뜻은 아니다. 예를 들어 저장 데이터가 아예 없는 최초 생성은 기존 데이터 갱신과 조건이 다르다. 이런 경계는 따로 다루고 있다. 구현은 [Anna 도구의 저장 처리](https://github.com/kdkrkwhr/notebook-pets/blob/cba0513803a96350d8807c2dc156b27ed3c8efbb/anna/executas/notebuddy/notebuddy_plugin.py)에 모아 두었다.

사용자 경험에서도 중요한 구분이 있다. **밥을 먹은 결과와 AI가 해 주는 말은 별개다.** 이미 저장된 돌봄 결과는 AI 답변이 늦거나 실패했다고 취소하지 않는다. 반대로 AI가 “배불러!”라고 말한 것만으로 게임 수치를 바꾸지도 않는다.

### 사용자별 기록은 어디에 남길까

Anna의 저장 기능인 APS를 사용하되, 데이터 성격에 따라 저장 위치를 나눴다.

| 데이터 | 보관 방식 |
| --- | --- |
| 친구 상태·성장·아이템·행동 처리 기록 | 인증된 사용자 범위의 도구 저장소 |
| 최근 대화와 그림을 찾기 위한 기록 | 사용자별 앱 저장소 |
| 원본 참고 그림과 생성한 초상화 | 파일 저장소에 보관하고 경로를 기록 |

앞의 코드에서 `actor_id="1"`을 보고 모든 사용자가 같은 친구를 공유한다고 생각할 수도 있다. 여기서 `1`은 **각 사용자에게 분리된 저장 데이터 안의 내부 슬롯**이다. 외부 사용자를 구분하는 경계는 Anna의 인증과 저장 범위에 있으며, 화면에서 임의의 다른 사용자 ID나 게임 상태를 보내도록 만들지 않았다.

그림도 생성 응답에서 받은 임시 URL만 저장하면 곤란하다. 파일 자체를 보관하고 그 경로를 기록해 둬야, 나중에 앱을 열 때 다운로드 주소를 다시 받아 보여 줄 수 있다. 친구의 그림이 다시 나타나는 경험 뒤에도 이런 저장 처리가 필요했다.

### 화면을 올렸다고 앱 전체가 바뀌지는 않았다

개발 중에는 화면이 정상적으로 열리는데 게임 도구 연결은 실패하는 상황을 따로 확인해야 했다. UI 번들과 Python 실행 도구는 서로 다른 배포 대상이기 때문이다.

게임 도구를 수정했다면 Windows·Linux 실행 패키지도 맞춰야 한다. 업로드 목록에 새 버전이 있는지에 더해, **설치된 화면이 어떤 도구를 호출하며 실제 실행 중인 도구가 무엇인지**까지 봐야 했다. 돌봄 행동을 한 뒤 앱을 다시 열어 결과가 남는지도 함께 확인했다.

개발 환경 자체에서 생긴 문제도 있었다. Windows 개발 연결에서는 한글 JSON이 CP949로 처리돼 깨지거나 저장 전에 오류가 난 적이 있다. 개발 실행 환경에 `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`을 명시하고 한글이 포함된 동작을 다시 확인했다. 이는 당시 **개발 브리지의 인코딩 문제**였으며, [검사 기록](https://github.com/kdkrkwhr/notebook-pets/blob/cba0513803a96350d8807c2dc156b27ed3c8efbb/anna/docs/PAID_TEST_20261017.md)에도 제품 동작과 구분해 남겼다.

### 이 분리가 다음 작업의 기반이 됐다

게임 규칙에서 파일과 플랫폼 호출을 떼어 둔 덕분에, 별도 웹 버전에서도 같은 Python 규칙을 재사용할 수 있는 기반이 생겼다. 저장과 AI 연결은 각 실행 환경에 맞게 붙인다. 다만 규칙을 공유하는 것과 사용자 데이터를 공유하는 것은 별개라서, Anna와 웹의 진행 상황이 자동으로 동기화되는 것은 아니다.

앱으로 옮기는 작업에서 가장 크게 배운 것은 **버튼의 응답과 저장된 결과를 함께 확인해야 한다**는 점이었다. 이 기반 위에서야 그림을 넣고 친구를 만나고, 그 친구의 성격과 기록을 이어 가는 경험을 붙일 수 있었다.

[3편]({{ '/ai/2026/10/19/notebuddy-character-growth.html' | relative_url }})에서는 그림 한 장이 초상화와 성격으로 이어지는 과정, 그리고 함께한 경험을 진화에 반영한 이야기를 다룬다.
